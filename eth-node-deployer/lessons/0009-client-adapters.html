Session 09 · Extensibility

Support multiple client pairs

Client diversity should add adapters, not fork the control plane.

By the endDefine a capability-based client contract and add a second documented client option without duplicating deployment orchestration.
01 / Mental model

Stable concepts surround variable implementations

Every pair needs image/version, network material, Engine API connection, P2P interfaces, data paths, metrics, and readiness probes. Exact flags and APIs vary. Model shared capabilities and let adapters produce client-specific runtime fragments.

Capability beats brand branching

Ask what the client supports—checkpoint sync, metrics, pruning, API auth—not whether its name matches scattered conditionals.

Compatibility is a matrix

Not every execution/consensus/network combination is valid. Validate the pair before persistence or provisioning.

Versions are inputs

Pin and record chosen versions so recovery recreates the intended runtime; upgrades are separate operations.

03 / Deliberate practice

Your 60-minute session

  1. 0–15: Read ethereum.org's run-a-node client list. Choose one additional execution or consensus client for a reason such as diversity or operational fit, then open its official docs.
  2. 15–28: Fill the capability matrix for the current and new option with source links. Record uncertain cells explicitly instead of guessing.
  3. 28–44: Author a stable client-selection type, compatibility parser/policy, and adapter interface that can produce the runtime inputs your Compose layer needs. Refactor the existing pair behind it.
  4. 44–53: Add tests for supported pairs, unsupported pairs, required capabilities, pinned versions, and adapter output that never changes control-plane state semantics.
  5. 53–60: Run tests/checks. Explain what adding a third client would change and what it must not change.
04 / Retrieval

Close the matrix

Which parts of the deployment lifecycle should change when adding a new execution client?
Reveal answer

Client-specific runtime configuration, capability validation, probes, and perhaps resource guidance change; durable deployment identity, tenancy, orchestration states, idempotency, and destroy policy should remain stable.
