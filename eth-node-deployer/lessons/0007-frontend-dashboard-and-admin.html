Session 07 · API operations

Connect commands to operations

The API records requests; the worker owns execution.

By the endImplement protected deploy, status, event-list, retry, and destroy-request contracts with idempotency and explicit authorization.
01 / Mental model

Commands and queries have different jobs

A command requests a transition and returns an operation identity quickly. A query reads persisted state or ordered events. Neither waits for infrastructure, shells into a host, or parses cloud logs inside the HTTP connection.

Commands need deduplication

A client retry with the same actor and idempotency key returns the existing operation instead of creating another deployment.

Queries need bounded views

Cursor events and deliberate public projections prevent unbounded reads and secret/internal-field leakage.

Destruction is policy

Authorize, confirm exact target, record request, let the worker destroy, verify absence, then retain an audit tombstone.

02 / Worked example

Define each contract before code

PROCEDURE CARDinput · actor · transition · output
deploy
  input: parsed configuration + idempotency key
  actor: approved user
  effect: deployment + queued attempt, transactionally
  output: deploymentId + operationId

status / events
  actor: owner or authorized operator
  effect: none; bounded read

retry / destroyRequest
  actor: policy-specific
  effect: legal durable transition, never inline cloud work
Write equivalent cards for all procedures. Stable public error codes should describe invalid input, unauthorized/hidden resource, illegal transition, conflict, and temporary failure.
03 / Deliberate practice

Your 60-minute session

  1. 0–12: Re-read tRPC procedures/middleware and your Phase 1 access matrix. Extend the matrix for infrastructure commands and operator views.
  2. 12–25: Write five procedure cards. Add transaction boundaries, idempotency uniqueness, public output fields, pagination cursor, and error mappings.
  3. 25–44: Author the procedures and repository operations. Keep the worker trigger behind an interface or durable queue signal; ensure command responses do not await provisioning.
  4. 44–54: Test duplicate deploy, cross-tenant status/events, illegal retry, destroy confirmation mismatch, and secret-free outputs. Include concurrency where your database supports it.
  5. 54–60: Run checks. Explain what happens if the response is lost after the database transaction commits.
04 / Retrieval

Close the API

A deploy request commits successfully but the network drops before the response arrives. What makes the client's retry safe?
Reveal answer

The same authenticated actor and idempotency key resolve to the already committed deployment/operation rather than enqueueing a second one.
