Session 10 · Observability

Define semantic readiness

A green status must say which claims were measured and when.

By the endImplement a client-neutral readiness evaluator from timestamped probe results and map each failure to operator evidence.
01 / Mental model

Readiness is a conjunction with freshness

Infrastructure exists, host configured, services reachable, execution client responsive, consensus client responsive, Engine link working, peers present, and sync close enough are separate signals. A stale success is not current evidence.

Measure the user promise

Process and port checks are dependencies. The user needs a documented RPC/node capability at an acceptable chain position.

Unknown differs from unhealthy

Timeout, unimplemented probe, stale sample, explicit false result, and incompatible client each drive different actions.

Logs explain; metrics trend

Structured events narrate operations, metrics reveal changing quantities, and traces correlate work. Do not force one tool to do all three.

02 / Worked example

Write the evidence ladder

READINESS CLAIMSprobe · threshold · freshness
cloud: instance expected state, sampled at ___
host: configuration revision verified, sampled at ___
runtime: required services healthy, sampled at ___
execution: documented RPC response + sync evidence
consensus: documented API response + sync evidence
engine: paired-client evidence, not merely shared JWT file
network: peer evidence appropriate to network/client

ready = required claims pass AND samples are fresh
degraded = useful but one non-critical claim fails
unknown = evidence absent/stale/unparseable
unhealthy = required claim explicitly fails
Derive actual methods, fields, and thresholds from each selected client's current docs and the disposable network's behavior. Record why a threshold is acceptable.
03 / Deliberate practice

Your 60-minute session

  1. 0–15: Read the selected clients' health/sync/metrics documentation. Audit the old Prometheus rules and sync script: state what each proves, misses, or assumes.
  2. 15–27: Write the evidence ladder with probe source, timeout, threshold, freshness, redaction, and user-facing meaning. Define ready, degraded, unknown, and unhealthy.
  3. 27–44: Author a pure evaluator over normalized probe results plus client adapters that normalize real response shapes. Keep raw vendor responses out of the domain status.
  4. 44–54: Test fresh success, stale success, zero peers, syncing, timeout, malformed response, and one client healthy while the other fails. Ensure reasons are actionable.
  5. 54–60: Run checks. Explain the exact evidence required before the database transitions to ready.
04 / Retrieval

Close the dashboards

Why must a readiness result include sample time or freshness policy?
Reveal answer

Because a once-successful probe can become stale after network, host, container, or client failure; without freshness the system presents historical evidence as current truth.
