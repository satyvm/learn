Define the durable deployment contract

A worker should recover from records, not from memory or log prose.

By the endExtend the Phase 1 data model with attempt, event, idempotency, client-selection, and secret-reference invariants sufficient for crash recovery.
01 / Mental model

Persist decisions and evidence separately

The deployment records desired service; attempts record executions; events/logs record ordered evidence; secrets live in a secret system and are referenced. Provider outputs are data, not status text.

Desired and observed differ

A requested client pair and an observed running pair can disagree during updates or failures.

Attempts are immutable history

Retries create new attempts while the deployment identity and tenant ownership remain stable.

Secrets are capabilities

Raw SSH keys, generated passwords, JWTs, and cloud credentials should not be casually returned or stored in ordinary rows.

02 / Worked example

Recover from the worst moment

CRASH THOUGHT EXPERIMENTbefore → crash → resume
1. worker claims attempt A
2. Pulumi creates EC2 instance i-123
3. process crashes before marking infrastructure_ready
4. worker restarts

Can records answer:
• which stack belongs to the deployment?
• whether another worker owns the attempt?
• whether i-123 should be reused or destroyed?
• which step is safe to repeat?
• what the user may see?
If an answer exists only in process memory or stdout, the model is not durable enough. Do not add columns without linking each to a recovery decision.
03 / Deliberate practice

Your 60-minute session

  1. 0–12: Retrieve your Phase 1 deployment/attempt invariants. Re-read the current schema and list every field that mixes intent, provider output, authentication secret, or lifecycle state.
  2. 12–27: Write recovery queries for: find current attempt, claim unowned work, resume a known stack, append ordered evidence, and list a user's deployments. Derive required constraints/indexes from the queries.
  3. 27–44: Update schema and migration to support deterministic stack identity, idempotency key, attempt lease/owner, client selection, output fields, and secret references. Avoid an unbounded free-text status.
  4. 44–53: Test constraint violations and tenant-scoped reads. Simulate a crash record after resource creation and prove your query identifies the resumable attempt.
  5. 53–60: Inspect generated SQL, run checks, and explain how duplicate request, duplicate worker, and leaked-secret risks are reduced.
04 / Retrieval

Close the database

Which identity must remain stable across retries: deployment, attempt, or worker process?
Reveal answer

The user-visible deployment and its deterministic infrastructure stack identity remain stable; attempts and worker ownership change while preserving history.
