Session 11 · Operations UI

Build the operator view

A calm dashboard answers what is happening, why, and what action is safe.

By the endExtend the authenticated UI with deployment state, freshness, ordered events, permitted recovery actions, and deliberate destructive confirmation.
01 / Mental model

The UI is a projection of durable policy

It must not invent lifecycle state from client-side timers or optimistic flags. It reads the server's public projection, renders uncertainty honestly, and offers only commands authorized and legal for the current actor/state.

Progress comes from events

Show current state plus a bounded ordered event history. Poll or refetch incrementally; do not simulate percentages.

Freshness is visible

Display when readiness was sampled and distinguish unknown, stale, degraded, failed, and ready.

Danger requires friction

Destroy names the exact deployment/resources, explains persistence consequences, requires deliberate confirmation, and reports asynchronous progress.

02 / Worked example

Design from operator questions

INFORMATION ORDERdecision before decoration
1. Which deployment and owner am I viewing?
2. What state is it in, and when was that evidence sampled?
3. Which step most recently succeeded or failed?
4. What evidence explains the failure without exposing secrets?
5. Which actions are legal for this actor and state?
6. What will retry or destroy do?
7. How will I know cleanup actually finished?
Sketch desktop and narrow-screen hierarchy before JSX. Use existing TanStack Router, Query, shadcn, and authenticated layout patterns rather than introducing another state system.
03 / Deliberate practice

Your 60-minute session

  1. 0–10: Retrieve the seven questions. Inspect the current dashboard, route layout, tRPC client, and shared UI package. Read only the Router/Query docs needed for parameter and refetch behavior.
  2. 10–22: Sketch list and detail screens for requested, active, ready, degraded/stale, failed, deleting, and deleted. Annotate data source and allowed action for each element.
  3. 22–45: Author the detail view and event list with a bounded update strategy. Add retry/destroy controls only when the server contract says they are permitted; include exact confirmation.
  4. 45–54: Exercise owner, other user, operator, stale evidence, long error text, empty events, request loss, and narrow viewport. Verify no credentials or raw provider errors render.
  5. 54–60: Run checks and the highest-value UI/API tests. Explain how the screen behaves during a worker restart.
04 / Retrieval

Close the UI

Why should the UI not infer readiness from the age of a client-side loading spinner or successful command response?
Reveal answer

Those are browser/request facts, not verified node facts; readiness must come from fresh persisted probe evidence owned by the backend workflow.
