Session 12 · Capstone

Run the controlled AWS canary

The final proof includes recovery and absence—not merely creation.

By the endDeploy one disposable testnet node through the application, prove readiness, recover from one bounded failure, destroy it, and inventory every expected resource as absent.
01 / Mental model

A canary is an experiment with exit conditions

You are testing a chain of claims against reality. Freeze scope, cap spend, preselect one safe disturbance, capture structured evidence, and preserve enough time to destroy even when creation fails.

Preflight is a gate

Confirm account/region, credentials, stack, estimated hourly/storage cost, expiry tags, quotas, client/network versions, and cleanup commands.

Failure is planned

Choose a recoverable disturbance such as worker restart after infrastructure or one stopped container. Never improvise destructive chaos.

Absence needs evidence

Pulumi destroy success is one signal. Inventory stacks, EC2, volumes, addresses, snapshots, secret references, and database tombstone.

02 / Worked example

Use a go/no-go sheet

CAPSTONE CONTROLapprove each gate
GO  local suite and repository checks pass
GO  preview matches reviewed resource inventory
GO  no world-open SSH/RPC/Engine/metrics/admin ports
GO  cost ceiling + time alarm + expiry tags recorded
GO  destroy path tested on disposable stack or reviewed
GO  one bounded failure injection selected
GO  no validator keys, funds, or mainnet scope

NO-GO if any expected output, permission, price, or cleanup target is unknown.
If provisioning or sync exceeds the session, do not rush. Stop at a safe persisted state, destroy if unattended cost is unacceptable, and continue in another scheduled session.
03 / Deliberate practice

The controlled run

  1. 0–10: Fill the preflight/go-no-go sheets with current AWS and client documentation. Run the entire local suite and inspect the final preview. Set a hard time for beginning cleanup.
  2. 10–25: Submit one deployment through the real UI. Observe operation ID, persisted transitions, Pulumi outputs, host steps, and redacted events. Do not repair state manually without recording why.
  3. 25–40: Prove readiness from execution, consensus, Engine pairing, peers, sync/freshness, and intended RPC access. Capture identifiers and timestamps, never secrets.
  4. 40–50: Inject the preselected bounded failure. Use only the product's retry/resume path. Confirm the same deployment/stack/resources recover and the event history explains what happened.
  5. 50–60+: Request destroy through the product. Verify Pulumi, AWS inventories, remote access, and database tombstone. Continue until every expected resource is absent or a documented retained resource has an owner/cost/reason.
04 / Retrieval

Defend the system

What evidence distinguishes a successful deployer capstone from a one-time successful node launch?
Reveal answer

The deployer proves durable intent, tenant policy, idempotent/resumable orchestration, fresh semantic readiness, explainable events, bounded recovery, deliberate destruction, and verified cleanup—not just a running client once.
