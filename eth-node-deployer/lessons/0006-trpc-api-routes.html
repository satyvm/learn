Session 06 · Orchestration

Build a durable operation runner

A worker advances persisted state one verified step at a time.

By the endAuthor and test a runner that claims one deployment attempt, executes injected steps, persists evidence, and resumes safely after a simulated crash.
01 / Mental model

Orchestration is not a long function

The runner reads durable state, acquires a lease, chooses the next legal step, invokes an adapter, verifies its result, persists transition/evidence, and releases or renews ownership. Frameworks and cloud SDKs stay behind injected boundaries.

Claim before work

Atomic lease/ownership prevents two workers from advancing the same attempt concurrently.

Checkpoint after verification

Persist a transition only after its postcondition is observed; on restart, probe external reality before repeating effects.

Classify failure

Retryable transport/provider failures differ from invalid configuration, unsafe state, cancellation, and exhausted attempts.

02 / Worked example

Simulate process death

TEST SCENARIOinject → crash → resume
Given attempt A is claimed by worker W1
And infrastructure adapter returns stable stack outputs
When the process dies before the next host step
And W1's lease expires
Then worker W2 claims A
And inspects the same stack identity
And does not create a second infrastructure stack
And resumes from the first unverified postcondition
You can prove this orchestration locally with fake adapters and a test database. Do not need real AWS to test state, leases, duplicate delivery, or crash timing.
03 / Deliberate practice

Your 60-minute session

  1. 0–12: Retrieve your state/event table and recovery queries. Write the runner loop as six English verbs, each with input, output, and persistence point.
  2. 12–25: Define interfaces for deployment repository, infrastructure adapter, host adapter, runtime verifier, clock, and structured event sink. Avoid importing Pulumi, SSH/SSM, or Hono into the core runner.
  3. 25–43: Author the smallest runner that advances one step. Make time and adapters injectable. Persist lease ownership and append evidence around the verified transition.
  4. 43–54: Test success, duplicate delivery, active competing lease, lease expiry, retryable failure, terminal failure, and the crash scenario above. Assert calls and durable state, not log prose.
  5. 54–60: Run tests/checks. Explain the exact point at which each side effect becomes safe to resume.
04 / Retrieval

Close the runner

What two mechanisms prevent a retried job from creating duplicate infrastructure?
Reveal answer

A lease serializes active workers, while a deterministic durable stack identity plus external-state probing makes the resumed operation target the same resources.
