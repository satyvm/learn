01 / Mental model

Intent and workload live in different planes

The web/API/database form a control plane that records intent and coordinates work. EC2, the host OS, containers, and Ethereum clients form the workload plane. A durable deployment/attempt record connects them without pretending one process owns the truth.

Intent precedes effects

A stable deployment ID exists before AWS calls so logs, retries, resources, and user actions share an identity.

Every boundary has a contract

API input, database record, Pulumi outputs, remote commands, Compose state, and client APIs each need explicit success/failure evidence.

Ready is layered

EC2 running, host reachable, containers healthy, clients peered, and chains synced are distinct claims.

For each artifact ask:
• what claim does it prove?
• what does it not prove?
• which new component will own that responsibility?
Do not copy the old Terraform/deploy flow into TypeScript. Treat it as a working specimen whose assumptions must be recovered and tested.
03 / Deliberate practice

Your 60-minute session

  1. 0–12: From memory, redraw the Phase 1 request path. Then read Ethereum's node architecture page and add execution, consensus, Engine API, and two P2P networks.
  2. 12–30: Inspect manual-node/eth-testnet/README.md, Terraform, deploy script, Compose services, and proof files. Build a table: component, input, output, owner, timeout, secret, and success evidence.
  3. 30–43: Draw the target architecture from browser to AWS and back. Mark synchronous versus durable asynchronous edges and the source of truth at every stage.
  4. 43–53: Write five failure scenarios at different boundaries. For each, state what the user sees and what evidence an operator reads first.
  5. 53–60: Explain why the manual flow works once but is not yet a multi-user control plane. Save the diagram near project documentation; write it yourself.
04 / Retrieval

Close the diagram

Why is “the EC2 instance is running” insufficient evidence that an Ethereum node is ready?
Reveal answer

It proves only the VM lifecycle; host initialization, disks, containers, Engine API authentication, peers, sync progress, and intended endpoints may still be unavailable or unhealthy.
