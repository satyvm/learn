Commits that evolve

Replace staging-area thinking with a working-copy commit and stable change identity.

By the endExplain change ID, commit ID, @, and @- from a jj status display.
01 / Mental model

Build the right picture first

Your working copy is a real commit marked @. Editing files changes its commit ID automatically, while its change ID remains stable across rewrites. @- is its parent.

Snapshotting is automatic

Most jj commands first snapshot tracked working-copy changes. There is usually no add/commit ceremony.

Change identity survives rewrite

A description edit, squash, or rebase produces new commit content and therefore a new commit ID, but the logical change ID remains.

The graph is visible

jj log shows working copy, parents, bookmarks, conflicts, and divergent changes in one DAG view.

02 / Worked example

Read status

ANNOTATED EXAMPLEread → predict → explain
Working copy  (@) : mzvwutvl 91c35e9a Add search
Parent commit (@-): qpvuntsm a12f418e main | Add API
                 ↑change ID ↑commit ID
Prefer change IDs when referring to evolving work. Commit IDs name exact immutable versions and remain useful for external Git interoperability.
03 / Deliberate practice

Do the work

Predict the result before each step. Keep a small note of what surprised you; surprise is useful evidence that your mental model changed.

  1. Initialize a disposable repo.
  2. Edit a file and run jj status.
  3. Run jj describe, edit again, and observe which ID changes.
  4. Draw @ and @-.
04 / Retrieval

Close the notes

Why are there two IDs?
Reveal answer

The commit ID identifies exact content and parents; the change ID follows the logical change as rewrites create new commit versions.
