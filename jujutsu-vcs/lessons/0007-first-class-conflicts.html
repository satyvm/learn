Conflicts can be committed

Understand why jj records conflicts and lets graph operations finish.

By the endCreate, inspect, resolve, and verify a conflicted change.
01 / Mental model

Build the right picture first

Jujutsu stores a logical conflict in commits. A rebase can complete with conflicted commits, descendants can continue to rebase, and resolution can happen at the appropriate change.

Conflict is state, not mode

There is no special rebase-in-progress ceremony. The graph marks conflicted commits and normal commands continue where meaningful.

Resolve at the introduction point

Find the earliest conflicted change, create or edit a working copy there, resolve files, inspect, and squash the resolution into that change.

Markers carry sides

Jujutsu’s markers may represent more than two sides and distinguish snapshots from diffs. Use jj resolve or edit deliberately.

02 / Worked example

Resolution loop

ANNOTATED EXAMPLEread → predict → explain
jj log -r 'conflicts()'
jj new <first-conflicted-change>
jj resolve              # or edit markers
jj diff
<run focused tests>
jj squash
jj log -r 'conflicts()'
Because descendants auto-rebase, resolving the earliest cause may clear conflicts later in the stack when their changes are independent.
03 / Deliberate practice

Do the work

Predict the result before each step. Keep a small note of what surprised you; surprise is useful evidence that your mental model changed.

  1. Create two changes that edit the same line.
  2. Rebase to create a conflict.
  3. Inspect conflict log and file markers.
  4. Resolve with intended semantics and squash.
  5. Verify no conflicts and run tests.
04 / Retrieval

Close the notes

Why can a jj rebase succeed while producing conflicts?
Reveal answer

Conflicted content is representable in commits, so graph transformation completes and resolution becomes a later explicit change.
