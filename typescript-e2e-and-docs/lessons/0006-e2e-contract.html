Session 06 · Foundations

Parse the create request

Zod is a runtime gate, not merely a source of TypeScript aliases.

By the endAuthor and test a Zod schema that converts an unknown deployment request into a normalized domain input.
01 / Mental model

Parsing is a phase change

External input is representation: strings, absent fields, and hostile values. Parsing returns either structured issues or a normalized value that downstream code may trust. Keep coercion, trimming, defaults, and compatibility rules at this edge.

Input and output may differ

A schema can accept one representation and produce a narrower domain value. Know which side a type describes.

Errors need stable paths

Field paths make form feedback possible; stable categories make logs and tests useful.

One authority

A handwritten type that drifts from the runtime schema creates false confidence. Derive or explicitly map.

02 / Worked example

Specify examples before schema methods

BOUNDARY TABLEraw → parsed or issue
region: " ap-south-1 "  → normalized region
network: supported value → domain network
network: unknown value   → issue at ["network"]
client pair: incompatible → cross-field issue
extra secret field        → reject or strip? decide explicitly
missing field             → default only if product policy allows it
A schema is correct relative to this contract, not because it compiles. Read Zod's pages for objects, enums, transforms, refinements, and error formatting only as needed.
03 / Deliberate practice

Your 60-minute session

  1. 0–12: Read Zod Basic usage plus the pages for APIs you expect to use. Write five accepted and five rejected examples before touching the schema.
  2. 12–22: Decide normalization, unknown-key behavior, defaults, and whether client compatibility belongs in this parser or a separate domain policy. Record why.
  3. 22–42: Author the create-deployment input schema in the package that owns the API/domain boundary. Infer its input/output types or map into the state model from Session 5.
  4. 42–53: Test all ten examples with safeParse. Assert issue paths for failures; do not snapshot an unreadable entire error.
  5. 53–60: Run focused tests and checks. Explain what runtime work the schema performs that a TypeScript type cannot.
04 / Retrieval

Close the schema

Why does successfully assigning an object to a TypeScript interface not make an HTTP request trustworthy?
Reveal answer

TypeScript checks declared program relationships and is erased at runtime; external bytes can violate those declarations until executable parsing validates and normalizes them.
