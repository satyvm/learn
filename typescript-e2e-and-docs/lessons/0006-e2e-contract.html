01 / Mental model

Build the right picture first

End-to-end type safety is a chain, and a chain is only as strong as its runtime boundaries. Test both compile-time expectations and executable policy.

Begin with an invariant

Write who may do what and which data must remain true before selecting abstractions.

Keep the public shape deliberate

Return what the interface needs, not raw tables. This creates freedom to change persistence.

Test seams

Schema rejection, authorization, mapping, and UI error states are higher-value than re-testing framework internals.

02 / Worked example

Contract ladder

unknown request

At each arrow ask: what evidence was gained, what failure is possible, and how is that failure represented?
03 / Deliberate practice

Do the work

Predict the result before each step. Keep a small note of what surprised you; surprise is useful evidence that your mental model changed.

  1. Choose a create or update feature.
  2. Write its invariant and public result.
  3. Implement parsing and authorization.
  4. Add invalid, forbidden, success, and retry tests.
  5. Remove every unexplained assertion.
04 / Retrieval

Close the notes

Does successful compilation prove the feature is safe?
Reveal answer

No. It proves consistency with declared types; runtime inputs, permissions, external failures, and incorrect declarations still require executable validation and tests.
