Session 03 · Foundations

Prove what unknown data contains

A type becomes trustworthy only after the runtime value earns it.

By the endAccept an unknown deployment candidate, narrow it without assertions, and test both accepted and rejected shapes.
01 / Mental model

Narrowing accumulates evidence

unknown means a value exists but no operations are yet justified. Each runtime check removes possibilities along one control-flow branch until property access or a function call becomes safe.

Check outer shape first

Exclude null, primitives, and arrays before asking an object for properties.

Validate every used field

A property existing does not prove its value type or membership in a supported set.

Test rejection paths

Boundary code is defined as much by what it rejects as by its happy path.

02 / Worked example

Build a proof tree

REASONING FRAMEbroad → specific
unknown
└─ non-null object?
   ├─ no  → reject with a stable reason
   └─ yes → required property exists?
            ├─ no  → reject
            └─ yes → value has expected primitive type?
                     ├─ no  → reject
                     └─ yes → supported domain value?
Write this decision tree before the function. Your branches should correspond to tests, and the compiler should narrow inside each successful branch.
03 / Deliberate practice

Your 60-minute session

  1. 0–12: Read TypeScript's narrowing page through user-defined type predicates. Predict which checks narrow object, arrays, strings, and literal unions.
  2. 12–22: In your domain file, write a truth table for a valid deployment candidate plus: null, an array, missing region, numeric region, and unsupported network.
  3. 22–43: Author a function accepting unknown that returns either a proven draft or a stable failure description. Use no any and no assertions. Let compiler errors tell you which proof is missing.
  4. 43–53: Add one test per truth-table row. Make a test fail intentionally, confirm the message points to the violated expectation, then repair it.
  5. 53–60: Run the focused tests and bun run check. Explain why typeof null and arrays require separate handling. Stop only when you can redraw the proof tree.
04 / Retrieval

Close the notes

Why does checking typeof value === "object" not justify reading value.region?
Reveal answer

Because the value may still be null, an array, or an object without that property; the property's existence and value type still require runtime evidence.
