Encode invariants in PostgreSQL

01 / Mental model

Three layers tell different truths

A domain type models valid application states. A Drizzle schema describes database objects and infers query types. PostgreSQL constraints are the final authority when concurrent processes or future code write data.

Identity survives retries

A user-visible deployment and an operational attempt have different lifetimes. Overwriting one row destroys failure history.

Constraints are executable policy

Foreign keys, uniqueness, nullability, enums/checks, and indexes should follow explicit invariants and access paths.

Migrations are reviewed code

Generate a diff, read the SQL, predict its effect on existing rows, then apply it to disposable local data.

02 / Worked example

Audit before editing

SCHEMA REVIEWinvariant → constraint → query
Inspect packages/db/src/schema/node.ts:

• Which columns describe user intent?
• Which describe one provisioning attempt?
• Which values are secrets and should not be here?
• Can two users receive the same stack identity?
• Can a log be ordered deterministically?
• Which common ownership query needs an index?
• What prevents an arbitrary status string?
The file already has uncommitted work. Treat it as the learner's current draft: inspect git diff, preserve intent, and change it only after writing the invariants.
03 / Deliberate practice

Your 60-minute session

  1. 0–15: Read Drizzle schema declaration and migrations fundamentals. Separately define primary key, foreign key, unique constraint, not-null constraint, enum/check, relation, and index.
  2. 15–27: Review the current schema and its diff. Write an invariant table with columns: rule, database mechanism, expected violating operation, and query needing an index.
  3. 27–43: Revise only the minimum schema needed to separate deployment intent from attempts and remove or isolate raw secret material. Export the schema deliberately.
  4. 43–52: Start local PostgreSQL, generate a migration, and read every SQL statement before applying it. If data could be destroyed, stop and explain the migration instead.
  5. 52–60: Apply to disposable data, inspect with Studio or SQL, then run checks. Explain the difference between a Drizzle relation and a database foreign key.
04 / Retrieval

Close the schema

Why keep deployment attempts separate from the deployment users recognize?
Reveal answer

Each retry has distinct provider identifiers, timing, logs, outputs, and failures; preserving attempts supports audit, diagnosis, idempotency, and recovery without changing the stable deployment identity.
