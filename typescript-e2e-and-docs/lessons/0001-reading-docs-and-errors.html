Read errors as a path

Turn intimidating diagnostics into a sequence of small comparisons.

By the endLocate the first meaningful mismatch in a nested TypeScript error.
01 / Mental model

Build the right picture first

A long error is usually a path through nested structure: assignment → property → callback → parameter. Read outside-in to learn the context, then inside-out to find the earliest false assumption.

Identify the operation

First ask what TypeScript was checking: assignment, function call, return, generic constraint, or overload selection.

Follow indentation

Repeated “is not assignable” clauses form a breadcrumb trail. The deepest specific mismatch is often actionable.

Inspect definitions

Go to definition and hover the receiving type. Documentation and declaration files reveal the contract more reliably than guessing.

02 / Worked example

Reduce the diagnostic

ANNOTATED EXAMPLEread → predict → explain
type User = { id: string; role: "admin" | "member" };
const user: User = { id: 42, role: "owner" };
// path 1: user.id → number is not string
// path 2: user.role → "owner" is outside the union
Fix one leaf at a time and rerun the compiler. Later errors may be consequences of the first incorrect shape.
03 / Deliberate practice

Do the work

Predict the result before each step. Keep a small note of what surprised you; surprise is useful evidence that your mental model changed.

  1. Copy one real error into a scratch file.
  2. State the checked operation in plain language.
  3. Underline the deepest mismatch.
  4. Inspect the target declaration before editing.
04 / Retrieval

Close the notes

In “argument callback is not assignable because its parameter is narrower,” which layer should you inspect first?
Reveal answer

The callback parameter contract—the deepest concrete mismatch—then work outward to understand why that callback was expected.
